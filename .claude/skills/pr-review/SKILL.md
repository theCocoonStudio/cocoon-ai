# PR review

Review a pull request the way a merge decision deserves: verify, do not skim; hold the PR to what it claims and to everything it does not exclude; report so the author can act without a second read. The reviewer is the required approval on `main`, so an approval that is not a real review makes the ruleset decorative.

Two principles, and everything below applies them:

**The floor is fixed; the ceiling is open.** Every review covers the same floor, in the same order, and says so. Above the floor the reviewer attacks the change however it can, and reports those findings in their own section, each with the evidence that earned it a place. The floor makes reviews comparable; the open ceiling is where a reviewer with more time or a different mind than the author's earns its keep.

**A finding is something the reviewer verified.** A suspicion is reported as a question, marked as one. Nothing is reported as a defect on a reading alone when it could have been run.

## Scope

- Any PR in this repo, by either author. The same floor for both; nothing is softer because the author is the reviewer's collaborator, and nothing is softer because the author is the reviewer.
- **Self-review.** Before opening a PR, the author runs this skill on it and puts the report in the PR body under "Self-review". A self-review approves nothing; it finds what the other reviewer would have found first.
- **What it is not.** Not a style pass: the formatter and the linter own style, and `npm run check` runs them. Not a redesign: a finding says what is wrong with the change as made, and may name a better shape, but the change's scope is the author's.

## The run

1. **Read the claim.** The PR title, body and commit messages: what the change is for, and what it declares out of scope or not yet done. A declared gap is recorded as declared, not found; everything not declared is held to the full standard. Note the base branch: a PR stacked on another is reviewed as its own diff.
2. **Take the branch.** Check it out locally. `git log --oneline main..HEAD` is the commit list; one commit per conceptual task, and each message says what and why. `git diff main...HEAD --stat` is the surface.
3. **Run it.** `npm run check` on the branch, in full. Then whatever the change adds that the check does not exercise: a script, run; an export, opened; a generated file, regenerated and diffed; a component, mounted in the test renderer if its tests do not already; a claimed number, measured. This is the step that turns a reading into a review.
4. **Walk the floor.** Every item below, every time, each with a one-line result in the report.
5. **Attack.** Above the floor, with the time left: inputs the author did not try, the sequence they did not think of, the size that breaks it, the consumer that imports it differently, the machine that lacks what this one has. Anything found goes in the report's "Beyond the floor" section with its evidence.
6. **Report.** In the shape below, then the decision.

## The floor

| Item | What is checked | Fails when |
|---|---|---|
| Claim | The change does what the title, body and messages say, and nothing they do not | Undeclared work in the diff; a declared thing missing |
| Check | `npm run check` passes on the branch: lint, format, knip, tests, build | Anything red; a test skipped without a stated reason |
| Tests | Every behaviour the change adds or alters has a test that fails without the change; negative cases included; test names trace to the spec ids where a spec exists | A behaviour with no test; a test that passes with the change reverted; a declared "no tests" gap is recorded, not failed |
| Spec | A component or util built through the spec skill has its spec, resolved spec, tests and doc, and the resolved spec's contracts and defaults match the code | Drift between spec and code; a resolved entry the code does not honour |
| Config | Design defaults come from `cocoon.config.js`; no reader restates a number | A literal where the config has the value |
| Generated | Generated files are regenerated by their build and committed byte-identical; nothing hand-edited | A regenerated file that differs; an edit to a generated file |
| Assets | Shipped assets that the change could move were rebuilt, and either did not move or the move is the point and is shown | A silent change to a shipped file |
| Disposal | Scene code releases what it creates: every geometry, material, texture and render target has its moment, on rebuild and on unmount; nothing runs per frame that sets React state; refs are read where the spec says | A leak; a per-frame render; a stale closure |
| Boundaries | Nothing at module scope touches `window` or `document`; nothing imports a peer the package does not declare; the library entry gains only named exports; `sideEffects` and pure annotations hold, so a consumer importing one export pays for one | A module-scope side effect; a new dependency without a `package.json` change and a reason; a bundle that grew for an unrelated import |
| Secrets and access | No credential, token, key, path to one, or private URL in the diff, the tests, the fixtures or the generated files; no network call the change does not need; no change to the sandbox, firewall or auth without saying so | Any of the above |
| Docs | The README's scripts table and layout, the component doc, the util doc and the spec files say what the code now does; a rename or a new option is swept through the repo | A doc that describes the old behaviour; a stale name |
| Commits | One commit per conceptual task; messages say what and why; decisions live in the repo, not only in the PR body | A commit that mixes tasks; a decision recorded nowhere but the conversation |

## The report

Posted as the review on GitHub, and, for a self-review, in the PR body. Sections in this order, headings kept, so two reviews of two PRs read the same way.

**Claim.** One paragraph: what the PR does, what it declares out of scope, which base it is on.

**Ran.** What was executed to verify the change, with results: the check, the scripts, the measurements. A review with an empty "Ran" section is a reading, and says so.

**Floor.** The table above as a list, one line per item: `pass`, `fail`, or `declared` for a gap the PR announced, each with the fact behind it. A `fail` names the file and line.

**Beyond the floor.** Findings the checklist did not ask for: what was tried, what happened, what it means for the change. Empty is a legitimate value and is written as "nothing found beyond the floor, tried: ..." so the attempts are visible. This section is where the reviewer is expected to bring something the author could not foresee; a review with nothing here on a non-trivial PR should say what it tried.

**Questions.** Suspicions the reviewer could not verify, as questions to the author. Never mixed with findings.

**Decision.** Approve, request changes, or comment, with the one sentence that decides it. Approve only if the reviewer would merge it. A request for changes names each change and, where the fix is mechanical, gives the exact command or edit.

## Rules the reviewer keeps

- **Never push to the branch under review.** A fix the reviewer wants is a request, with the exact change, or a PR of its own after this one merges. Why: on 2026-09-03 the reviewer pushed a commit onto a branch it then approved, so its own commit became mergeable with no review.
- **Never approve a PR containing the reviewer's own commit.**
- **Never merge.** Merging is the author's, on their own call.
- **A declared gap is not a finding.** It is recorded under "Floor" as `declared` and, if it should be closed, under "Questions" or "Decision" as a follow-up, not as a defect.
- **Verify before reporting.** If a claim in the PR can be checked in under a minute, check it. If it cannot, say it was not checked.
- **Report faithfully.** A failing check is quoted, not summarised. A number is the measured one. Nothing is softened because the author is a friend, and nothing is inflated because the reviewer found it.

## Definition of done

The report has every section, the "Ran" section is not empty, every floor item has a result with a fact, and the decision follows from the floor and the findings rather than from the tone of the PR. If the review took a shortcut, the report says which.
