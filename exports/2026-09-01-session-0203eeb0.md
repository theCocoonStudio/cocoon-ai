## Claude · 2026-09-02 01:27:02

Worth it in principle, awkward in practice with this specific setup. Straight tradeoff:

**What rootless buys.** The daemon and every container run as your unprivileged user. A container escape lands as that user, not root. With rootful Docker, membership in the `docker` group is root-equivalent on the box, so the container is the only wall.

**What breaks with rootless Docker here.**
- **Bind-mount ownership.** In rootless mode your host UID maps to root inside the container, and the container's `node` user (UID 1000) maps to a subordinate UID on the host. So `/workspace` shows up as owned by root and `node` can't write to your repo. Docker rootless has no clean "keep my UID" option.
- **The firewall.** `iptables` + `ipset` inside a rootless container need the kernel modules preloaded on the host by root (`ip_tables`, `iptable_filter`, `xt_set`, `ip_set_hash_net`), and ipset in a user namespace is hit-or-miss depending on kernel and nftables backend.

**Two ways to go.**
1. **Rootful Docker, `docker` group, on the dedicated box.** Accepts root-equivalence on a machine that holds nothing but a public repo clone and one scoped token. Works with `run.sh` as written. This is what I'd do given the box is itself the outer wall.
2. **Podman rootless** instead of Docker. Rootless by default, `--userns=keep-id` maps your UID straight through so the bind mount just works, and NET_ADMIN inside the rootless netns is supported. `run.sh` needs small edits (`podman` for `docker`, add `--userns=keep-id`, drop the volume for `~/.claude` or adjust ownership) and the same modprobe list once. The firewall's ipset step is the piece to test first.

If you want the extra layer, say "podman" and I'll adapt `run.sh` and note the host modules to load. Otherwise carry on with what you have.

userns=keep-id:uid=1000,gid=1000 -- same user?


## Claude · 2026-09-02 01:36:52

Yes, that's the point of it: you inside the container.

Rootless podman runs everything in a user namespace. By default your host UID becomes root (0) inside, and the container's other UIDs map to a subordinate range from `/etc/subuid`. That's what breaks the bind mount: your repo would show up as root-owned and the `node` user couldn't write to it.

`--userns=keep-id` maps your host UID to the same number inside instead. The `:uid=1000,gid=1000` suffix says: whatever my host UID is, map it to 1000 inside, which is the `node` user the image already has. So:

- files you own on the host are owned by `node` inside, and files `node` creates inside are owned by you on the host
- no `chown` games, no orphaned UIDs in the repo
- if your Debian user happens to be UID 1000 already, the suffix changes nothing; it just makes it not depend on that

One consequence to know: with keep-id, root inside the container is a different mapped UID, not you. `sudo` for the firewall script still works because the setuid mechanics stay within the namespace, but that's the first thing to confirm on the box, since it's the one rootless-specific piece.
